---

NVIDIA discloses driver vulnerabilities through PSIRT security bulletins. The
bulletins carry a CVE identifier, a one-sentence description, a CWE, a CVSS
vector and the affected driver branches. They rarely name an ioctl, an escape
code, a Resource Manager control command or a source function, so the disclosed
history establishes the layer and the weakness class and stops there.

Two device-node populations divide the record. `nvidia.ko` and `nvidia-uvm.ko`
expose `/dev/nvidiactl`, `/dev/nvidiaN`, `/dev/nvidia-uvm` and
`/dev/nvidia-uvm-tools` to any process holding those nodes, at whatever
privilege the process already has. Everything else in the GPU display driver
package reaches a different attacker: the Windows kernel-mode driver
`nvlddmkm.sys`, the user-mode driver libraries, the vGPU host plugin, the
installer, `nvidia-modeset`, and GPU firmware. The classification below keeps
the two populations apart and holds a third group for the disclosures where
NVIDIA's own wording does not decide which one applies.

## Sources

Three sources carry the record, and only the second holds every bulletin.

| Source | Coverage | Form |
| --- | --- | --- |
| [github.com/NVIDIA/product-security](https://github.com/NVIDIA/product-security) | Bulletins first published 2022 to 2026 | Markdown, CSAF and CVE Record Format, one directory per bulletin |
| [nvidia.com/en-us/security](https://www.nvidia.com/en-us/security/) | Every bulletin, including those predating the repository | HTML |
| [NVD API 2.0](https://services.nvd.nist.gov/rest/json/cves/2.0) | 2018 to 2021 bulletins, where NVIDIA is the assigning CNA | JSON |

NVIDIA began publishing bulletins to the GitHub repository on 1 October 2025,
backfilling to 2022. Bulletins from 2018 to 2021 were recovered from NVD, which
carries NVIDIA's own CVE descriptions because NVIDIA is the CNA for them.

The machine-readable form of this page, one record per CVE with the
classification and its basis, is `surface/prior-cves.json`.

## Classification method

Each CVE is assigned to one of four buckets. The rules run in the order below, and
the first that matches decides. Every record carries the rule that decided it.

| Rule | Outcome |
| --- | --- |
| NVIDIA names the NVIDIA Container Toolkit | Container Toolkit |
| A published researcher writeup names the kernel module and the entry point | Kernel modules |
| NVIDIA names the Virtual GPU Manager, the vGPU plugin, a host driver, a user-mode layer, the installer, a D-Bus configuration file, GPU firmware, VBIOS, NVKMS or modeset | Outside both |
| NVIDIA lists Windows platforms only, or scopes the sentence to the Windows driver | Outside both |
| The CVSS attack vector is not `AV:L` | Outside both |
| NVIDIA names `DxgkDdiEscape` or `nvlddmkm.sys`, lists Linux drivers as affected, and names no Linux entry point | Undetermined layer |
| The affected-product list names no operating system and the sentence names no Linux module | Undetermined layer |
| NVIDIA names the kernel mode layer, the kernel driver, a kernel module, `nvidia.ko`, the Unified Memory driver or UVM, on a Linux platform with a local attack vector | Kernel modules |
| Otherwise | Undetermined layer |

The `Outside both` bucket collapses several distinct exclusions into one label.
A Windows-only defect and a vGPU host defect are both outside the local Linux
ioctl surface for different reasons, and the per-record `classification_basis`
field in `surface/prior-cves.json` keeps them apart.

The 61 kernel-module CVEs fall by bulletin year as 1 in 2020, 3 in 2021, 26 in
2022, 15 in 2023, 4 in 2024, 6 in 2025 and 6 in 2026. Two bulletins dominate
the count. Bulletin [5415](https://nvidia.custhelp.com/app/answers/detail/a_id/5415)
of December 2022 carries 19 and bulletin
[5452](https://nvidia.custhelp.com/app/answers/detail/a_id/5452) of March 2023
carries 12. Both were large batch fixes against the Linux kernel mode layer,
and the descriptions inside each batch are close to identical, which limits how
much the batch says about distinct code paths.

## Kernel-module disclosures

Vulnerabilities NVIDIA places in `nvidia.ko` or `nvidia-uvm.ko`, reachable
over ioctl on the device nodes an unprivileged local process holds. All 61 are
tabulated on [Driver CVEs](/gspwn/reference/surface/driver-cves/), which is
generated from `surface/prior-cves.json` and carries the bulletin date, the
bulletin link, the CWE, the CVSS base score, the subsystem and NVIDIA's own
component-and-fault sentence for each one, together with what reading the
fixing diff established about where the fix lives.

Seven of the 61 have a public source naming the module, the entry point or the
faulting function. Those seven are in [Disclosures with published technical
detail](#disclosures-with-published-technical-detail) below. For the other 54
NVIDIA's sentence is the whole public record.

reached by handing malformed bytes to a parser.

## Published work on fuzzing this surface

Five published works target this driver family.

| Work | Venue and date | Target | Descriptions published |
| --- | --- | --- | --- |
| [Moneta](https://www.ndss-symposium.org/ndss-paper/moneta-ex-vivo-gpu-driver-fuzzing-by-recalling-in-vivo-execution-states/) | NDSS 2025, Yonsei University and KU Leuven | NVIDIA 530.41.03 open kernel modules, AMD Radeon, ARM Mali | Yes, at [github.com/yonsei-sslab/moneta](https://github.com/yonsei-sslab/moneta) |
| [StepStone](https://www.cs.ucr.edu/~zhiyunq/pub/oakland26_gpu_fuzzing.pdf) | IEEE S&P 2026, UC Riverside | NVIDIA, AMD and Mali drivers through CUDA and Vulkan user-space libraries | Not located |
| [Fuzzing the NVIDIA GPU Drivers](https://interruptlabs.co.uk/articles/fuzzing-the-nvidia-gpu-drivers) | Interrupt Labs, July 2026 | `nvidiactl`, `nvidiaN`, `nvidia-uvm`, `nvidia-uvm-tools` and the DRM nodes | No |
| [BSOD](https://github.com/0xf4b1/bsod-kernel-fuzzing) | RAID 2021 | Binary-only driver fuzzing, the public version tailored to NVIDIA | Prototype published |
| KernelGPT | Cited by StepStone as prior work | Automatic syzlang generation from kernel source by a large language model | Generated NVIDIA descriptions do not compile, per StepStone's evaluation |

Upstream syzkaller carries no NVIDIA descriptions. At commit `1e72964b` of
17 August 2026, the only match for "nvidia" under `sys/linux/` is the
`typec_nvidia` sysfs path inside `auto.txt`, which belongs to the USB Type-C
alternate-mode driver.

Moneta's vendored syzkaller tree holds the only public NVIDIA syzlang, in
`go/src/github.com/google/syzkaller/sys/linux/sys.txt`. It declares 30 named
variants of `syz_ioctl_nvidia` plus a generic form, one per NV_ESC escape,
covering the allocate, free, control, map, unmap, duplicate, share, export and
import families. Six properties bound what it reaches.

| Property | Value |
| --- | --- |
| Device nodes in `dev_nvidia` | `/dev/nvidia0`, `/dev/nvidiactl`, `/dev/nvidia-modeset` |
| UVM nodes | Absent |
| Escape enumeration | Complete for the escapes it names, keyed on the `_IOWR` size and the `'F'` magic |
| Payload type for every escape except `NV_ESC_IOCTL_XFER_CMD` | `array[int8, N]`, an untyped byte run of the correct length |
| `NVOS54_PARAMETERS.cmd`, the RM control multiplexer | Unmodelled |
| RM object class numbers | Unmodelled |

The escape space is therefore enumerated in public and the payload space is
not. A byte-array payload reaches the escape dispatcher and mutates the control
command number as random bytes, so a control command's own parameter block is
reached only by chance. The size of that unmodelled space is on
[RM control command surface](/gspwn/knowledgebase/rm-control-surface/): 1372
exported methods behind the single `cmd` field.

Interrupt Labs report writing syzlang for `nvidiaX`, `nvidiactl`,
`nvidia-uvm`, `nvidia-uvm-tools` and the DRM nodes, including `NV_ESC_RM_ALLOC`
and `NV_ESC_RM_CONTROL`, extracting constants with `syz-extract` against the
`open-gpu-kernel-modules` headers. The descriptions are not published, no
repository is named, and the article records no vulnerabilities found in
fuzzing runs of about a day. It also records that syzkaller's `setuid` sandbox
blocks access to the DRM nodes and that `namespace` does not.

StepStone reports that KernelGPT's generated NVIDIA descriptions reference over
60 missing structure or type definitions and do not compile under syzkaller
once the syntax errors are corrected. Its own 11 NVIDIA bugs name the functions
they fired in: `devmem_page_to_chunk_locked`, `uvm_mmu_chunk_unmap`,
`uvm_page_mask_test`, `portMemCmp`, `block_phys_page_address`, `mapFind_IMPL`,
`uvm_gpu_chunk_get_gpu`, `nvidia_mmap_helper`, `remove_proc_entry`, and two
NVKMS assertions. Seven of the eleven came through CUDA APIs and four through
Vulkan.

## Limits of the disclosed record

| Question | State of the public record |
| --- | --- |
| Which NV_ESC escape a given CVE reaches | Answered for two CVEs out of 61 |
| Which RM control command a given CVE reaches | Answered for none |
| Which RM object class a given CVE involves | Answered for none |
| Which UVM ioctl a given CVE reaches | Answered for one, CVE-2025-23300 |
| Whether a given CVE is reachable from a container with `compute,utility` | Asserted for CVE-2025-23282 and CVE-2025-23332, unstated for the rest |
| Which driver branch first introduced a defect | Never stated. Bulletins give the fixed version and never the introducing one |

Any statement about which ioctl a historical CVE reached, absent one of the
seven researcher sources above, is an inference. Reading the driver's own tags
between the affected and updated versions narrows it no further for most of the
record: `surface/cve-hotspots.json` places 4 of the 61 in a named function, 4
more plausibly, leaves 45 not located, and cannot resolve 8 at all, because
NVIDIA backfilled the PSIRT repository only to 2022 and no bulletin text is
cached for the older ones.
