A container has no access to a GPU by default. Device nodes and driver
libraries live on the host and enter a mount namespace only when something
bind-mounts them there. The NVIDIA Container Toolkit performs that injection,
as root, in the window after the namespaces exist and before the container's
own process starts.

## Stages

| Stage | Component | Runs as | Input it parses |
| --- | --- | --- | --- |
| 1 | The image and its OCI configuration | Supplied by the caller | Image labels, entrypoint, environment |
| 2 | `containerd` or `dockerd` | root | The create request |
| 3 | `nvidia-container-runtime` | root | `NVIDIA_*` environment variables, the OCI spec |
| 4 | `nvidia-container-runtime-hook` | root | The container's config and root filesystem path |
| 5 | `libnvidia-container` through `nvidia-container-cli` | root, in the target namespaces | The driver installation, the ldcache, the requested capabilities |
| 6 | The image entrypoint | The image user | Nothing from the toolkit |

Stage 3 is a shim around `runc`. It reads the request, rewrites the OCI
specification to add a prestart hook, and hands the modified specification to
the real runtime. Stage 5 moves the files: it resolves every driver library by
name, follows the ldcache, and bind-mounts the results plus the device nodes
into the container's mount namespace.

## Capabilities

`NVIDIA_DRIVER_CAPABILITIES` selects which groups of libraries and device nodes
are injected. The default is `compute,utility`. The full value-to-node mapping,
the environment variables that bypass it, and the difference between the two
injection mechanisms are on
[Container device access](/gspwn/knowledgebase/container-device-access/).

## Environment variables

| Variable | Selects |
| --- | --- |
| `NVIDIA_VISIBLE_DEVICES` | Which GPUs are exposed: `all`, an index list, a UUID list, or `void` for none |
| `NVIDIA_DRIVER_CAPABILITIES` | The driver capability set, honoured by the legacy hook only |
| `NVIDIA_REQUIRE_CUDA` | A version constraint the host driver must satisfy, checked before the container starts |
| `NVIDIA_DISABLE_REQUIRE` | Skips the constraint check |

These are read from the image as well as from the run command. An image can
carry `NVIDIA_VISIBLE_DEVICES=all` in its own environment, so a caller who
passes no GPU flag can still get every GPU on the host if the runtime is
configured to honour image-supplied values.

## Two injection mechanisms

| Mechanism | Device description | Applied by | Selected when |
| --- | --- | --- | --- |
| Legacy hook | Implicit. The hook resolves the driver installation at container creation time. | `nvidia-container-runtime-hook` calling `nvidia-container-cli` | `mode` is set to `legacy` |
| CDI | Explicit. A YAML or JSON specification lists every device node, mount and hook. | Any CDI-aware runtime, with no NVIDIA-specific shim | `mode` is `cdi`, or `jit-cdi`, which `mode = "auto"` resolves to on a host where NVML loads |

The toolkit ships with `mode = "auto"`, so a current installation on a
discrete-GPU host runs the CDI mechanism and generates the specification in
memory at container creation time.

CDI is the Container Device Interface, a runtime-agnostic specification.
`nvidia-ctk cdi generate` writes a file under `/etc/cdi/` describing each
device as a named entity such as `nvidia.com/gpu=0`, and a CDI-aware runtime
applies it directly. The resolution work moves from container creation time to
specification generation time.

## Worked example: docker run --gpus all under the legacy hook

The sequence below traces `mode = "legacy"`. The CDI mechanism replaces steps
3 through 5 with a generated specification, and selects a different device set.
See [Container device access](/gspwn/knowledgebase/container-device-access/).

1. The caller runs `docker run --gpus all <image>`. Docker translates `--gpus`
   into a device request and calls `nvidia-container-runtime`.
2. The shim reads `NVIDIA_VISIBLE_DEVICES` and `NVIDIA_DRIVER_CAPABILITIES`,
   taking values from the run command first and from the image environment
   otherwise. Neither is set here, so it resolves to every GPU and the
   `compute,utility` capability set.
3. The shim inserts a `prestart` hook into the OCI specification and calls
   `runc create` with it.
4. `runc` sets up the namespaces and the root filesystem, then runs the hook
   before executing the entrypoint.
5. The hook calls `nvidia-container-cli configure`, which enters the
   container's mount namespace and bind-mounts `libcuda.so`,
   `libnvidia-ml.so`, `nvidia-smi` and the `compute,utility` device nodes into
   it, then updates the container's ldcache.
6. `runc start` executes the entrypoint. The process sees `/dev/nvidiactl` and
   a `libcuda.so` matching the host driver, and can open both.

Steps 3 through 5 all run as root on the host. Step 6 is the first one that
runs as the image's user.
