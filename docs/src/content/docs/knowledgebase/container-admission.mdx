A container starts with no access to a GPU. Device nodes and driver libraries
are host paths, and they appear inside a mount namespace only when something
bind-mounts them there. The NVIDIA Container Toolkit performs that injection,
as root, in the window after the namespaces exist and before the container's
own process starts.

runs every one of the six stages.

## Stages

Six stages run between the create request and the container's first
instruction, and the mechanism in force decides which of them execute.

| Stage | Component | Runs as | Input it parses | Runs under |
| --- | --- | --- | --- | --- |
| 1 | The image and its OCI configuration | Supplied by the caller | Image labels, entrypoint, environment | Both mechanisms |
| 2 | `containerd` or `dockerd` | root | The create request | Both mechanisms |
| 3 | `nvidia-container-runtime` | root | `NVIDIA_*` environment variables, the OCI spec | Both mechanisms |
| 4 | `nvidia-container-runtime-hook` | root | The container's config and root filesystem path | Legacy hook only |
| 5 | `libnvidia-container` through `nvidia-container-cli` | root, in the target namespaces | The driver installation, the ldcache, the requested capabilities | Legacy hook only |
| 6 | The image entrypoint | The image user | Nothing from the toolkit | Both mechanisms |

Stage 3 is a shim around `runc`. It reads the request, rewrites the OCI
specification, and hands the modified specification to the real runtime. What
it writes into the specification depends on the mode. Line references are to
`nvidia-container-toolkit` at commit `1780ac6`.

| Mode | Stage 3 writes into the specification | Stages 4 and 5 |
| --- | --- | --- |
| `legacy` | A prestart hook pointing at `nvidia-container-runtime-hook` (`internal/modifier/stable.go:65`) | Both run |
| `cdi`, `jit-cdi` | The device nodes, mounts and hooks a CDI specification names, applied directly. Any existing NVIDIA prestart hook is removed (`internal/modifier/hook_remover.go:44`) | Neither runs |

On the legacy path, stage 5 moves the files. It resolves every driver library
by name, follows the ldcache, and bind-mounts the results plus the device nodes
into the container's mount namespace.

## Capabilities

`NVIDIA_DRIVER_CAPABILITIES` selects which groups of libraries and device nodes
are injected. The default is `utility,compute`
(`internal/config/image/capabilities.go:46`). The full value-to-node mapping,
the environment variables that bypass it, and the difference between the two
injection mechanisms are on
[Container device access](/gspwn/knowledgebase/container-device-access/).

## Environment variables

| Variable | Selects |
| --- | --- |
| `NVIDIA_VISIBLE_DEVICES` | Which GPUs are exposed: `all`, an index list, a UUID list, or `void` for none |
| `NVIDIA_DRIVER_CAPABILITIES` | The driver capability set, honoured by the legacy hook only |
| `NVIDIA_REQUIRE_CUDA` | A version constraint the host driver must satisfy, checked before the container starts |
| `NVIDIA_DISABLE_REQUIRE` | Skips the constraint check |

These are read from the image as well as from the run command. An image can
carry `NVIDIA_VISIBLE_DEVICES=all` in its own environment, so a caller who
passes no GPU flag can still get every GPU on the host if the runtime is
configured to honour image-supplied values. That behaviour is on by default:
`accept-nvidia-visible-devices-envvar-when-unprivileged` ships as `true`
(`api/config/v1/config.go:106`).

## Two injection mechanisms

The two differ in when the device set is resolved and in which runtime applies
it.

| Mechanism | Device description | Applied by | Selected when |
| --- | --- | --- | --- |
| Legacy hook | Implicit. The hook resolves the driver installation at container creation time. | `nvidia-container-runtime-hook` calling `nvidia-container-cli` | `mode` is set to `legacy` |
| CDI | Explicit. A YAML or JSON specification lists every device node, mount and hook. | Any CDI-aware runtime, with no NVIDIA-specific shim | `mode` is `cdi`, or `jit-cdi`, which `mode = "auto"` resolves to on a host where NVML loads |

The toolkit ships with `mode = "auto"` (`api/config/v1/config.go:120`), and
`auto` resolves to `jit-cdi` on any platform where NVML or WSL is detected
(`internal/info/auto.go:129`). A current installation on a discrete-GPU host
therefore runs the CDI mechanism and generates the specification in memory at
container creation time.

CDI is the Container Device Interface, a runtime-agnostic specification.
`nvidia-ctk cdi generate` writes a file under `/etc/cdi/` describing each
device as a named entity such as `nvidia.com/gpu=0`, and a CDI-aware runtime
applies it directly. The resolution work moves from container creation time to
specification generation time.
