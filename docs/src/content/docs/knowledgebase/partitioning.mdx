Five mechanisms divide one GPU between consumers. They differ in where the
boundary falls, which decides what one consumer can observe or disturb about
another.

<PartitionModes />

## Comparison

Each mode is placed by where its boundary falls, what memory a consumer sees,
what a fault reaches, how work is scheduled, and what the mode requires.

| Mode | Boundary | Memory | Fault containment | Scheduling | Requires |
| --- | --- | --- | --- | --- | --- |
| Passthrough | PCIe function assigned to one guest, DMA fenced by the IOMMU | The whole frame buffer | A guest reset affects that guest | The guest owns the device | IOMMU, a hypervisor |
| Time-slicing | Context switch in the GPU scheduler | Per-context virtual address spaces | A fatal fault can reset the device for every context | Round-robin between contexts | Nothing. It is the default. |
| MPS | Per-client, inside one shared context, from Volta onward | A separate address space per client on Volta and later. One shared address space before it. | Contained to the faulting client on Volta and later. Before it, a fault kills every client. | Concurrent submission, with no switch between clients | The MPS control daemon |
| MIG | SMs, L2 cache slices and memory controllers assigned to an instance | A fixed share of the frame buffer, physically partitioned | A fault stays inside its instance | Each instance schedules independently | A100 or later data centre part |
| vGPU | Host-side mediation of register access | A fixed share per guest | A guest reset affects that guest | The host manager schedules guests | Licensed vGPU software, a supported part |

MPS raises throughput above time-slicing by removing the context switch, and
its isolation depends entirely on the architecture. MIG is the only mode where
the division is made in silicon.

## Time-slicing

Multiple CUDA contexts exist on one GPU and the scheduler switches
between them. Each context has its own virtual address space, so one cannot
address another's memory. The contexts share every SM, the full frame buffer
bandwidth and the failure domain.

Compute preemption arrived with Pascal and made the switch finer. Before it, a
long-running kernel held the GPU until it finished. With it, the scheduler can
preempt at instruction granularity, so one tenant's long kernel no longer
stalls another's short one indefinitely.

## MPS

The Multi-Process Service replaces per-process contexts with one shared
context, fronted by a control daemon. Work from several processes is submitted
into that single context and runs concurrently without a switch between them.

Volta changed the isolation properties substantially.

| Property | Pre-Volta MPS | Volta and later |
| --- | --- | --- |
| Address space | One, shared. A client can address another client's allocations. | One per client. A client cannot address another's memory. |
| Fatal fault | Ends the shared context and every client with it | Contained to the faulting client for most fault classes |
| Resource limits | None | `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` caps a client's SM share |
| Client submission | Through the daemon | Direct to the GPU, with the daemon out of the submission path |

Even on Volta and later, MPS shares SMs, L2 and memory bandwidth with no
partition between clients, so one client's traffic degrades another's
throughput. `CUDA_MPS_ACTIVE_THREAD_PERCENTAGE` caps the share of SMs a client
may occupy, and memory bandwidth stays uncapped. MPS therefore bounds what a
client can read and leaves what a client can consume open, which suits
cooperating co-tenants such as the ranks of one MPI job. Mutually untrusted
tenants need MIG.

## MIG

Multi-Instance GPU divides the hardware itself. An A100 exposes seven compute
slices and eight memory slices, and a partition takes a whole number of each.

The split is two levels.

- A GPU Instance divides the physical GPU. It holds memory slices, SM slices,
  L2 slices and its own memory controllers.
- A Compute Instance divides one GPU Instance. It holds SM slices within that
  GPU Instance, and the Compute Instances inside one GPU Instance share that
  instance's memory.

### Profile names

Five profiles are defined on an A100 40GB.

| Profile | Compute slices | Memory slices | Frame buffer | Instances that fit on an A100 40GB |
| --- | --- | --- | --- | --- |
| `1g.5gb` | 1 | 1 | 5 GB | 7 |
| `2g.10gb` | 2 | 2 | 10 GB | 3 |
| `3g.20gb` | 3 | 4 | 20 GB | 2 |
| `4g.20gb` | 4 | 4 | 20 GB | 1 |
| `7g.40gb` | 7 | 8 | 40 GB | 1 |

The number before `g` is compute slices and the number before `gb` is frame
buffer. The two do not track each other. `3g.20gb` takes three of the seven
compute slices and four of the eight memory slices, so two of them exhaust the
memory while leaving a compute slice with nothing to pair with. That asymmetry
makes some combinations unbuildable even where the compute count allows them.

Each instance appears as its own device. `nvidia-smi -L` lists them with their
own UUIDs, and `/dev/nvidia-caps/` carries the capability files that gate
access to each one.
[Container device access](/gspwn/knowledgebase/container-device-access/) states
the three routes by which those capability files reach a container.

## vGPU

A licensed host-side driver presents a mediated device to each guest. The guest
runs an NVIDIA guest driver and addresses the mediated device as a physical
GPU. The host manager schedules the guests onto the device and mediates
register access. Profiles fix the frame buffer per guest, so a 16 GB card
divided into four 4 GB profiles serves four guests.

vGPU and MIG compose. A MIG instance can back a vGPU profile, which gives the
guest a hardware-partitioned share in place of a time-shared one.
