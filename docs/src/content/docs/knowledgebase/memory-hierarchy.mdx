GPU storage is layered, and capacity and bandwidth move in opposite directions
at every step. Each level below the registers buys roughly an order of
magnitude of capacity and costs roughly an order of magnitude of bandwidth. The
figure carries the capacity, bandwidth and latency of each level for one H100
SXM.

## Levels

Six levels run from a thread's registers to host memory, each with its own
scope and its own manager.

| Level | Scope | Managed by |
| --- | --- | --- |
| Registers | One thread | The compiler, at compile time |
| Shared memory | One thread block | The programmer, explicitly |
| L1 data cache | One SM | Hardware, sharing the array with shared memory |
| L2 cache | The whole device | Hardware, with a programmer-settable residency policy |
| Device memory | The whole device, and peers over NVLink | The driver's allocator |
| Host memory | The system | The operating system, reached over PCIe or NVLink |

The L1 array and shared memory are one physical structure with a configurable
split, so raising the shared memory carve-out lowers the L1 available to the
same SM. `cudaFuncSetAttribute` with
`cudaFuncAttributePreferredSharedMemoryCarveout` sets the split per kernel.

## Transaction sizes

The hardware moves fixed quantities, and the ratio of bytes requested to bytes
moved is the effective bandwidth.

- A sector is 32 bytes, the unit of an L2 to device-memory transfer.
- A cache line is 128 bytes, four sectors, and the unit of L1 tagging.
- A warp memory instruction is serviced as the set of sectors the 32 lanes
  touch.

A warp whose 32 lanes read consecutive 4-byte values covers 128 contiguous
bytes, which is 4 sectors. The same warp reading with a 128-byte stride touches
32 separate sectors and moves 1024 bytes to deliver 128, an eightfold loss with
no change to the source apart from an index expression.

## Shared memory banking

Shared memory is divided into 32 banks of 4-byte words, addressed so that
consecutive words fall in consecutive banks.

| Access pattern across a warp | Cost |
| --- | --- |
| Each lane hits a different bank | One transaction |
| Several lanes hit the same address in one bank | One transaction, broadcast |
| Several lanes hit different addresses in one bank | Serialised, one transaction per distinct address |

The last row is a bank conflict. A two-dimensional array of 32 floats per row,
accessed column-wise, puts every lane in the same bank and serialises 32 ways.
Padding the row to 33 floats shifts each row by one bank and removes the
conflict. Tiled kernels carry that padding for this reason.

## L2 residency control

From Ampere onward, a portion of L2 can be reserved for a named address range
so that repeatedly read data is not evicted by streaming traffic.

- `cudaDeviceSetLimit` with `cudaLimitPersistingL2CacheSize` sets how much L2 is
  set aside.
- `cudaStreamSetAttribute` with an access policy window sets which address range
  is treated as persisting, and the hit ratio to aim for.

## ECC

Data centre parts carry error-correcting codes on device memory. Single-bit
errors are corrected and counted. Double-bit errors are uncorrectable and
raise an Xid.

| Property | Behaviour |
| --- | --- |
| Usable capacity on HBM parts | Unchanged. HBM2e and HBM3 carry dedicated ECC storage, so the check bits cost no user-visible capacity or bandwidth. |
| Usable capacity on GDDR parts | Reduced. Where ECC is implemented by reserving part of the same memory, both capacity and bandwidth fall. |
| Counters | Volatile and aggregate counts, per memory location, from `nvidia-smi -q -d ECC` |
| Retirement | Pages accumulating errors are retired so allocations avoid them |

`nvidia-smi -e 0` disables ECC and requires a GPU reset to take effect. Consumer
parts have no ECC on device memory.
